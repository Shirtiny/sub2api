## 4. 分层核对结论

| 层级 | 观察结果 |
|---|---|
| 上游 `chatgpt.com/backend-api/codex` | 原始终止 usage 明确包含 `cache_write_tokens: 0` |
| Aether 上游解析 | 记录 input/cached/write/output 与原始终止 usage 一致 |
| Aether 下游输出 | 相关 token 字段与上游响应一致，没有把非零写入改成 0 |
| Sub2API 用量拆分 | `普通输入 = 上游 input - cached - cache_write`，三条样本逐项相等 |
| Sub2API 费用 | 缓存写入 token 为 0 时，缓存写入费用为 0；其他费用按各自 token 与价格计算 |

因此，在已核对样本中，`cache_write_tokens=0` 不是 Aether 或 Sub2API 丢字段造成，而是上游响应的明确值。

## 5. 与官方公开资料的边界

- [OpenAI Prompt Caching 文档](https://developers.openai.com/api/docs/guides/prompt-caching)说明：GPT-5.6 及后续模型的写入通过 `cache_write_tokens` 报告，写入价格为普通输入的 1.25 倍；`implicit` 是 `prompt_cache_options.mode` 的默认值。
- 调查时的 OpenAI Codex 官方源码提交为 `9e552e9d15ba52bed7077d5357f3e18e330f8f38`（2026-07-11）。其 [Responses 请求结构](https://github.com/openai/codex/blob/9e552e9d15ba52bed7077d5357f3e18e330f8f38/codex-rs/codex-api/src/common.rs)包含 `prompt_cache_key`，但没有 `prompt_cache_options`；其 [终止 usage 解析](https://github.com/openai/codex/blob/9e552e9d15ba52bed7077d5357f3e18e330f8f38/codex-rs/codex-api/src/sse/responses.rs)只消费 `cached_tokens`，没有消费 `cache_write_tokens`。
- `api.openai.com` 开发者 API 文档与 `chatgpt.com/backend-api/codex` 订阅后端不是同一入口。仅凭本地观测无法判定 Codex 后端返回 0 是既定计量合同、阶段性实现差异还是上游缺陷。

## 6. 不能从现有数据推出的结论

- 后续 `cached_tokens` 增长说明缓存可被读取，但不能反推出前一请求应计费的精确 `cache_write_tokens`。
- `input_tokens - cached_tokens` 不是可靠的缓存写入值，其中还包含普通未缓存输入；隐式/显式断点位置也不可从总 token 唯一还原。
- 因此，不应根据相邻请求的 cached 增量回填或补扣缓存写入费用。若需要严格采用开发者 API 的官方写入计量，应使用能按请求返回非零 `cache_write_tokens` 的标准 API 渠道，并以原始 usage 为准。
